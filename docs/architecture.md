# Architecture

## Layout

| Path | Role | May depend on |
|---|---|---|
| `core/` | Beat engine, sampler, reverb, A/B logic, view, mapping, mirror protocol | `hal/hal.hpp`, LVGL |
| `core/config/` | `beat_config.hpp` (every tunable), `control_map.hpp` (every mapping) | nothing |
| `core/samples/` | Sample table; `sample_data.cpp` is generated by `tools/pack_samples.py` | nothing |
| `hal/hal.hpp`, `hal/controls.hpp` | Interface | nothing |
| `hal/esp32/` | I2S, display, LEDs, buttons, I2C | ESP-IDF |
| `hal/sim/` | SDL audio, framebuffer, input injection | SDL2 |
| `firmware/` | `app_main`, tasks, mirror sender | all of the above |
| `sim/` | Replica, keyboard, serial client | all of the above |

`core/` contains no hardware `#ifdef`s. The HAL is resolved at link time. Firmware and simulator compile the same `core/` sources.

| `core/` module | Job |
|---|---|
| `beat/engine` | Transport, seed capture and commit, layer lifecycle, drum and layer playback, status |
| `beat/layer` | One layer: quantized seed, fade-in ramp, mutation |
| `beat/drums` | One generated drum bar from seed accents and activity |
| `audio/sampler` | 32-voice sample player with gain buses and click-free stealing |
| `audio/reverb` | Stereo reverb |
| `ui/buttons` | A/B chord state machine (docs/controls.md section 2) |
| `ui/view`, `ui/led_view` | LVGL screen, LED strip |

## Tasks

| Task | Core | Priority | Rate | Job |
|---|---|---|---|---|
| audio | 1 | MAX-2 | 2.9 ms | `BeatEngine::render`: commands, keys, sequencing, generation, sampler, reverb; then a blocking I2S write |
| input | 0 | 10 | 1 ms | Buttons, keys, encoders |
| ui | 0 | 5 | 5 ms | A/B logic, encoders, LVGL, LEDs |
| mirror | 0 | 2 | 50 ms | Optional framebuffer stream |

All are pinned, which ESP-IDF requires for tasks that use the FPU.

Data crosses tasks without locks:

- **Keys:** input task to audio, through a single-producer single-consumer ring. Live notes start within one block.
- **Buttons, encoders:** input task to UI, through a second ring.
- **Commands** (select instrument, clear layer, clear all): UI to audio, through a third ring.
- **BPM, reverb targets:** UI to audio, through `std::atomic<float>`.
- **Status** (loop position, layers, fades, seed countdown, peak): audio to UI, through relaxed atomics. Fields may tear against each other for one frame, which is harmless for a display.

`static_assert`s in `engine.hpp` prove these atomics are lock-free on both targets. A test runs 5 layers, drums, reverb at maximum and live keys for 20,000 blocks and requires zero heap allocations.

All generation runs in the audio task on fixed arrays: seed capture (64 notes), layers (6 slots of 96 notes), the drum bar (16 x 4), mutation at each loop start, drum generation at each bar start. Each is a bounded loop of a few hundred iterations, at most once per 16th.

## Signal path

```
32 x [ sample (flash, int16, 22.05 kHz) -> linear interpolation -> amp ramp -> bus gain ]  mono sum
  -> reverb (mono in, stereo out, added to dry) -> master gain -> soft clip -> int16 stereo, 44.1 kHz
```

- **Buses:** one per layer slot (6), generated drums, live play. Layer fades, evictions and clears ramp the bus gain linearly across each chunk, so no step reaches the output.
- **Voices:** position in Q20.12 fixed point. Pitch ratio $r = 2^{(n - n_\text{root})/12} \cdot \frac{22050}{44100}$. Attack 2 ms, release per sample (from the manifest), steal and choke fade 6 ms. A stolen voice fades out, then starts the new note.
- **Stealing order:** idle voice, then the quietest releasing voice, then the oldest loop or drum voice, then the oldest live voice.
- **Timing:** each block is split at 16th boundaries, so every step fires on its exact frame. BPM changes only the step rate, never the phase, so the tempo glides (time constant 0.3 s) without losing sync.
- **Reverb:** 4 damped combs, 2 series allpasses, 1 allpass per output, 26 kB. The amount sets wet level and comb feedback, gliding with a 50 ms time constant.
- **Soft clip:** $y = x - \frac{4}{27}x^3$ for $|x| \le 1.5$: unity slope at 0, reaching $\pm 1$ with zero slope.

## CPU budget

One core gives $240 \times 10^6 / 44{,}100 = 5{,}442$ cycles per stereo sample. Target: under 60 %, or 3,265 cycles.

**Not measured on an ESP32-S3.** No hardware was available. Rough estimate, assuming 2 cycles per instruction and flash reads mostly hitting the cache (each voice reads sequentially):

| Block | Cycles per sample |
|---|---|
| One voice (index, 2 loads, interpolation, ramp, bus gain) | about 50 |
| 32 voices, all busy (worst case) | about 1,600 |
| Reverb | about 200 |
| Output, soft clip | about 60 |
| Sequencing and generation, averaged | under 20 |
| **Worst case total** | **about 1,900, or 35 %** |

Typical play uses 5 to 15 voices, about 10 to 20 %. On the host, `danger_bench` gives 0.26 % of real time with 14 voices; that shows relative cost, not device speed. Cache misses on flash sample reads are the main unknown. The `CPU n %` readout on screen measures the real load from the cycle counter after first boot. If the load is too high, the first steps are fewer voices (`kVoices`), copying the most-used samples to RAM, or moving the voice loop to IRAM.

## Memory

From the linker, `danger` build:

| Item | Bytes |
|---|---|
| Static RAM total | 122,352 of 327,680 |
| of which `App` (engine, layers, sampler, reverb about 26,000) | 37,160 |
| of which LVGL heap | 32,768 |
| of which LVGL draw buffer | 25,600 |
| Task stacks, from the heap | 36,864 |
| Mirror shadow, from the heap, 15 x 10,240 | 153,600 |
| Flash (code, fonts, 514,644 of samples) | 1,060,115 of 3,145,728 |

`danger-nomirror`: 113,888 B static RAM, 1,048,355 B flash. Static RAM fell by about 50 kB against the synth build (no delay line).

Samples are `const` and stay in flash, read through the cache; they cost no RAM. **RAM is the tightest resource**, as before: the mirror's 153,600 B shadow comes from the heap and only fits if the heap regions beyond the linker's segment are available as expected. That has not been confirmed on hardware. If it does not fit, the mirror turns itself off and logs the reason; audio, UI and input keep running.
